# production のサイト自動公開

対象は Doppelar/yoshiokacho、Vercel doppelars-projects/web、
https://web-olive-ten-47.vercel.app/ のみ。

## 現在の問題

- production のブランチ保護がなく、既存 Code Check / Integration Tests は main・develop のみを対象にしていた。
- 旧 deploy.yml は main・develop の push で DB と Supabase 認証設定を更新していた。
- PR #7 は web のデプロイ成功後も、本番 URL が長野県を準備中として配信していた。
  デプロイ成功と本番 URL への割り当てを同一視しない。
- 別プロジェクト yoshiokacho の Git 連携も動作中。切断は Vercel 管理権限で実施する必要がある。

## フロー

1. production から作業ブランチを作る。
2. PR で lint・型チェック・ビルド・単体テスト・ローカル Supabase 統合テストを実行する。
3. Codex が安全なサイト変更と判断した PR に site-autopublish ラベルを付ける。
4. repository owner が作った同一リポジトリの PR だけを自動マージ候補にする。
5. 対象ファイル、削除・リネームなし、最新 SHA の CI、Vercel – web の成功を確認する。
6. 現在の production 自体の本番検証成功が確認できる場合だけ squash merge する。
7. Vercel Git 連携が web の本番ビルドを実行する。
8. /api/deployment の SHA と projectId、および本番ページ・地図のリンクを確認する。
9. 検証失敗時は Actions を失敗にし、以降の自動マージを止める。自動ロールバックや DB 操作はしない。

自動マージは SITE_AUTOPUBLISH_ENABLED=true が設定されるまで動作しない。
GITHUB_TOKEN のマージでは別の push Actions が起動しないため、
自動マージ後に Verify production を明示的に dispatch する。
Vercel 連携によるデプロイが起動しなければ本番検証が失敗し、その後の自動マージを停止する。

## 自動化しない変更

自動化対象は地域別地図のデータ・表示、地方版更新履歴、既存地域ページの表示、
所定の画像フォルダに限定する。
DB、認証、Server Actions、環境変数、依存関係、Actions、インフラ、API、
ファイル削除・リネームなどはラベルを付けても自動マージしない。
追加の manual-review / db-change / secrets / destructive ラベルでも停止する。
これらはユーザーに変更内容を提示して事前承認を得る。
許可パスの拡張も手動レビュー対象。

## 有効化前に承認が必要な設定

- GitHub の既定ブランチを production に変更する。
- production を保護し、lint-and-typecheck、integration-test、Vercel – web を必須にする。
  古いベースへのマージを禁止、force push・削除を禁止、管理者にも適用する。
- Vercel web の Production Branch が production であること、
  本番ドメインが正しいプロジェクトに属すること、自動 Production domain assignment が有効なことを確認する。
- Vercel の別プロジェクト yoshiokacho の Git 自動デプロイを停止する。
- Verify production の初回成功後、SITE_AUTOPUBLISH_ENABLED=true を設定する。

ブランチ保護や既定ブランチなどの設定は、ワークフロー変更だけでは適用されない。
PR としてレビューした後、ユーザー承認を得て API で設定する。
既定ブランチを production にするまで、workflow_dispatch などのトリガー条件も確認する。
環境変数値は取得・変更せず、/api/deployment は非秘密の SHA と projectId だけを返す。
Vercel がこれらのシステム環境変数を公開していない場合、検証は成功扱いにしない。

## 停止・復旧

SITE_AUTOPUBLISH_ENABLED を false にすれば新しい自動マージを停止できる。
本番検証失敗の原因と Actions Summary を確認し、対象コミット・プロジェクト・URL の割り当てを修正する。
DB や秘密情報が原因でも、値の取得・変更前にユーザーへ相談する。
Verify production を同じ production SHA で再実行し、成功するまで自動マージを再開しない。
監視は HTTP と配信 JS の確認であり、全画面のブラウザ操作や DB 機能テストを代替しない。

## 検証

node --test .github/scripts/*.test.js
pnpm lint
pnpm typecheck
pnpm build
pnpm test

CI の Integration Tests は使い捨てローカル Supabase のみを使用する。
既存 Supabase に対する db push や config push は本フローでは実行しない。

## 旧 DB ワークフロー

deploy.yml は手動実行に変更し、確認文字列と対象環境を必須にした。
DB 更新後の Deploy Hook 呼び出しは削除した。main/develop の既存コミットにある
旧ワークフローは今回書き換えないため、これらのブランチへ push しないこと。

Supabase Previewの実サービス操作も、ユーザー承認後の db-preview-approved ラベルを必須にした。
既定ブランチは調査時点で claude/mirai-gikai-fork-sync-ibv3cu だったため、productionへの統一は別途承認して適用する。

## レビュー解決後の再試行

レビュー未解決で停止した場合、修正のpushは synchronize により再検証される。
コメントの解決だけの場合は、site-autopublish ラベルを一度外して付け直す。
本番検証が未成功ならラベルを付け直しても自動マージしない。
ブランチ保護の適用案は .github/production-protection.json に保存した。
